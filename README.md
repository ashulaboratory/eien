# Eien — 永遠の仲間とのSNS

> 学校生活や部活動など、長い時間を共に過ごしてきた「永遠の縁」のある仲間と、
> 安心して長く使い続けられるクローズドなSNSをつくります。

---

## 概要

Eien は招待制・通知最小限のクローズドSNS。React 19 (TypeScript / Vite) + Go (Echo) + PostgreSQL 16 で構築し、Fly.io 東京リージョンにデプロイすることを想定している。本リポジトリ単体で、認証・グループ・投稿・誕生日通知バッチが動作する MVP まで実装済み。ローカルで `make dev-up` から数コマンドで全機能を立ち上げられる構成になっている。

## 開発ステータス（2026年5月時点）

### 実装済み

**バックエンド (Go + Echo)**

- 認証：新規登録 / ログイン / ログアウト / `/me` / 認証ミドルウェア（セッション Cookie + bcrypt）
- グループ：作成 / 一覧 / 詳細 / メンバー一覧 / 招待リンク発行 / 招待リンクからの参加
- 投稿：作成（画像添付対応・トランザクション）/ グループ単位の一覧 / 詳細取得 / 削除
- タイムライン：所属グループ横断の投稿取得 API
- 誕生日通知バッチ：cron による毎朝 7:00 JST 自動実行 + 手動実行用エントリポイント (`cmd/birthday/main.go`)
- メーラー：開発時は Mailhog に SMTP 送信（本番 SMTP は差し替え予定）
- 自動マイグレーション：サーバ起動時に `db/migrations/` を順次適用

**フロントエンド (React 19 + Vite)**

- 認証画面：ログイン / 新規登録
- グループ画面：一覧 / 新規作成 / 詳細 / 招待リンク受諾
- 投稿画面：新規投稿（画像アップロード対応）
- タイムライン画面：所属グループ横断の投稿表示
- ルーティング：認証必須/不要の分離（`ProtectedRoute`）、共通レイアウトのネスト

> **注:** 現状の UI は、Web アプリケーション全体の流れ（ルーティング・認証フロー・バックエンド API との疎通）が想定通りに動作するかを確認するための簡易実装である。本番リリース時に想定している UI/UX デザインとは別物であり、デザインの作り込みは今後の Phase で行う予定。

**インフラ**

- `fly.toml` 設定済み（東京リージョン `nrt`）
- `docker compose` によるローカル PostgreSQL + Mailhog 起動

## 起動方法

**前提ツール**: Docker, Go 1.26+, Node.js 22+, [golang-migrate](https://github.com/golang-migrate/migrate)

```bash
# 1. 環境変数を準備
cp .env.example .env

# 2. PostgreSQL + Mailhog をコンテナで起動
make dev-up

# 3. DB スキーマを適用（サーバ起動時にも自動適用されるが、明示的に流す場合はこちら）
make migrate-up

# 4. バックエンドを起動（:8080）
make backend-run

# 5. 別ターミナルでフロントエンドを起動（:5173）
cd frontend && npm install && npm run dev
```

アクセス先:

- フロントエンド: [http://localhost:5173](http://localhost:5173)
- バックエンド API: [http://localhost:8080/api](http://localhost:8080/api)
- Mailhog Web UI（送信メール確認用）: [http://localhost:8025](http://localhost:8025)
- DB シェル: `make db-shell`

その他のコマンドは `make help` で一覧表示できる。

## 背景

高校のクラスメイトや、大学で所属していたサークル。近い距離で長く過ごしてきた人とも、いつか別れの時は訪れる。私は2026年3月に、五年間通った高専を卒業した。五年間ずっと同じ教室で顔を合わせてきたクラスメイトは、これからも長く付き合っていきたい人ばかりだ。けれど、それぞれが進学や就職で別々の道に進み、しばらく顔を合わせられない仲間も少なくない。

それでも、たまにでいいから、あの人たちが今どう過ごしているのかは知っていたい。あの五年間を共に過ごした仲間のことを、忘れたくない。あの関係を「思い出」にしたくない。今もまだ続いている、現在進行形の縁でいたい。結婚や出産の節目があったら祝ってあげたい。たまに見かけて、元気そうだなと思えるだけでいい。

そういう願いを叶える手段として、これまで既存のSNSを使ってきた。SNSで繋がっていれば、わざわざ連絡を取り合わなくても、相手の投稿から日常を知ることができる。

けれど、いつ頃からか、SNSをやめたい自分がいた。SNSはどれも中毒性が強く、本来繋がりたかった相手よりも、見知らぬ誰かに時間を奪われていく。SNSから距離を置けば、リアルの時間でできることが確かに増える——そんな実感も持っていた。

それでもやめられなかった。理由はシンプルで、SNSをやめれば仲間との繋がりが同時に切れてしまうからだ。またSNSをやめるという選択をとった友人もいるが、皮肉なことに、そういう「リアルを大事にした人」とは既存のSNSでは繋がれなくなる。

たまに元気か見られればいいだけなのに、そのために中毒性のあるSNSに居続けなければならない——そんな矛盾した構造に巻き込まれていた。これは私だけの問題ではないはずだ。SNSとの距離を見直したいと思いながら、仲間との接続が既存のSNSに独占されているせいで、離れる選択肢を実質的に持てない人は多い。リアルを大事にしたい人ほど、接続維持のために妥協させられる構造になっている。

ならば、「たまに見られるだけのSNS」を作ればいい。中毒性に依存せず、リアルの時間を奪わず、それでも長く繋がっていられる場所が欲しい。

だから「広く浅く」ではなく「狭く長く」を価値にしたSNS、Eien を作ることにした。

## コンセプト

高校、大学、部活、サークル、職場——場所も期間も人それぞれだが、「長く同じ時間を過ごしてきた仲間」を持つ人は多い。Eienは、そうした人たちと永遠に繋がっていられる場所を提供する。

**永遠の仲間とのSNS**

Eienの根底にある思想は、「たまに見られればいい」という距離感を保つことだ。毎日触らせて滞在時間を伸ばす既存SNSの設計とは反対の方向を取り、ふと開いて仲間の近況を眺める、それで終わる使い方を許容する。

中毒性に依存しない控えめな設計だからこそ、リアルの時間を大事にしたい人にとっても無理なく続けられる。SNSとの距離を見直したい人や、SNSをやめてしまいがちな人も、Eienには残ってくれる。これまで既存のSNSでは繋がれなくなっていた「リアル重視の仲間」とも、Eienなら自然な距離感で繋がっていられる。

そうした繋がりが長く続いていくほど、Eienは「人生のマイルストーンが自然に流れていく場」になっていく。結婚や出産、転職や引っ越し——日常のひとコマから人生の節目まで、無理なく届く場所として残る。

この距離感を支える設計として、3つの原則を持つ:

- **招待制で、メンバーを固定する。** 不特定多数を相手にせず、「長く同じ時間を過ごしてきた仲間」だけが集まる場を作る。
- **通知を最小限にする。** 毎日のようにユーザーをSNSに引き戻すための仕組みは置かない。
- **「深く長く」使える体験を目指す。** 投稿頻度や滞在時間を煽る設計を排し、たまにふと開く、という距離感を保てるようにする。

## ターゲットユーザー

Eienは、個人ではなくグループ単位で価値を発揮するSNSである。次のような「長く同じ時間を過ごしてきた仲間グループ」を想定している。

- **学生時代を共にしたグループ** — 高校・大学のクラス、部活、サークルなど。卒業や進学で物理的に離れていく中で、ゆるく繋がり続けたい仲間。
- **職場・チーム単位のグループ** — 同じプロジェクトや部署で密度の高い時間を過ごしたメンバー。転職や異動で散らばっても、当時の関係性を残しておきたい仲間。
- **地元・幼馴染グループ** — 子供の頃から長く付き合いがあり、互いの人生の節目を見届けてきた仲間。

そして、こうしたグループの中でも、Eienは次のような志向を持つ人に特に響くサービスである:

- 既存SNSの「不特定多数のつながり」では満足できず、自分たちだけの閉じた場を求めている。
- **中毒性のあるSNSとの距離を見直したいが、仲間との接続を失う恐れから既存SNSから離れられずにいる。**
- 仲間の様子は「毎日チェック」ではなく、「たまに知れればいい」という距離感で十分だと感じている。
- 日常の連絡が減っても、人生の節目には確実に届く繋がりを残しておきたい。

## 技術選定およびその意図

本プロジェクトの個人的な学習動機は「初めてのバックエンド開発に取り組み、フロントエンドからバックエンド、データベース、インフラまでフルスタックで設計・実装できる状態を作る」ことだった。フロントエンドは既に経験があったため、新規挑戦の中心はバックエンド側（言語・フレームワーク・データアクセス・認証・デプロイ）に置いている。

そのため技術選定はバックエンド側から開始した。最初に Go を「初めてのバックエンド言語」として選び、それを起点に Web フレームワーク（Echo）や認証実装（bcrypt + セッション）が決まっていった。バックエンドの整理がついた段階でデータベース（PostgreSQL）を選び、それに連鎖してデータアクセス層（sqlc + pgx）とマイグレーションツール（golang-migrate）が連動して決まった。フロントエンドは経験のある React を中心に組み、最後にインフラ・デプロイ層を選定した。以下に各レイヤーの選定理由を示す。

### バックエンド

学習動機の中心がバックエンド習得だったため、未経験の Go を採用した。それを起点に Web フレームワーク・認証・定期実行などを連動して選定している。

- **言語: Go** — シンプルな文法と学習リソースの厚さを重視。研究・業務で経験のある Python を避け、未経験言語を学ぶ動機を優先した。
- **Web フレームワーク: Echo v4** —公式ドキュメントの構造が学習者向けに整理されている。Ginとの詳細比較をあまり行わなかったが人気やドキュメントの多さからGinを選択してもよかったとも思う。
- **認証ハッシュ: bcrypt** — `golang.org/x/crypto/bcrypt` の API が簡潔で取り回しやすい。Argon2 が現代の推奨である点は認識しているが、本プロジェクトの規模・脅威モデルでは bcrypt で十分と判断。
- **認証戦略: セッションベース** — DB の `sessions` テーブルを使うことで強制無効化が容易。認証のたびにサーバーアクセスが必要となるが、大規模なアプリではないので許容。
HttpOnly Cookie + SameSite で標準的な XSS/CSRF 対策をする

### データベース・データアクセス層

バックエンドが Go + Echo に決まった段階で、Go から扱う前提でデータベース層を選定した。まず DB として PostgreSQL を採用し、その結果としてデータアクセス層（sqlc + pgx）やマイグレーションツール（golang-migrate）が連鎖的に決まっていった。

- **DB: PostgreSQL 16** — UUID・JSON・配列などのネイティブ機能が充実しており、Eien のデータモデル（UUID 主キー、関係性のあるエンティティ）と相性が良い。MySQL より機能で、SQLite より本番運用適性で、MongoDB より関係モデル適性で優位と判断。Fly.io が公式サポートしている点も決め手。
- **データアクセス層: sqlc + pgx** — sqlc は自分が書いた SQL がそのままコード生成される設計で、ORM 的な裏側の不透明さを避けられる。型安全な Go コードが自動生成されるため、`Scan` のカラム数ズレなどを実行時ではなくコンパイル時に検出できる。GORM のような ORM は N+1 問題に気づきにくくなる懸念で見送った。pgx は sqlc が公式対応しているドライバを採用。
- **マイグレーション: golang-migrate** — Go 界隈で最も広く使われており、トラブルシューティング情報が豊富。

### フロントエンド

フロントエンドは既に経験のある技術で固定し、新規挑戦の学習リソースをバックエンド側に集中させる方針を取った。

- **UI ライブラリ: React 19** — 既に経験があり学習コストを抑えられる。Eien に必要な機能（コンポーネント設計、状態管理、ルーティング・データフェッチライブラリとの統合）に過不足がない。
- **言語: TypeScript** — 静的型チェックで実行前にバグを検出できる。バックエンドで Go を採用した「型安全な開発体験」をフロント・バック双方で揃えるため。主要ライブラリ（React、React Router、TanStack Query など）が TypeScript ファーストで型定義を提供している点も評価。
- **ビルドツール: Vite** — HMR による高速な開発サイクルが Webpack ベースに比べて大幅に速い。
- **スタイリング: Tailwind CSS v4** — 既に経験がある。ユーティリティクラス（`p-4 bg-blue-500 rounded` のような形）でクラス命名・CSS ファイル管理の悩みから解放される。
- **データフェッチ:**React のデータフェッチ用ライブラリ。 素の `fetch + useEffect` だとキャッシュやローディング状態の管理を自前で 書く必要があるが、TanStack Query にはそれらが標準で含まれていると聞いて採用した。
- **ルーティング: React Router 7** — reactのルーティングのデファクトと認識していたため採用した。本プロジェクトでは、認証チェック `ProtectedRoute`) と共通レイアウト `Layout`) を親ルートに集約し、各ページを 子ルートとして配置するネスト構造を活用している。

### インフラ・デプロイ

学習プロジェクトとしてのコスト・運用シンプルさを優先しつつ、本番リリースまで通せる構成を選定した。

- **デプロイ先: Fly.io** — `fly deploy` 1コマンドで Docker イメージを本番反映できる手軽さ、東京リージョン（nrt）の選択可能、PostgreSQL の公式サポート、小規模なら低コストな料金体系が決め手。
- **コンテナ: Docker（マルチステージビルド）** — Fly.io が Docker イメージを単位とするため必須。
