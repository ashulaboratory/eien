## 1. Web フレームワークの基礎概念

Webフレームワーク（Echo, Gin, Express など）は、本質的に次の流れを**抽象化**してくれる:

```
HTTPリクエスト → ルーティング → ハンドラ関数 → レスポンス
```

### HTTPリクエストとは

ブラウザがサーバーに「○○してほしい」と頼む通信。4つの要素を持つ:

| 要素 | 例（Eien の登録時） |
| --- | --- |
| **メソッド** | `POST`（作成）/ `GET`（取得）/ `PUT`（更新）/ `DELETE`（削除） |
| **URL（パス）** | `/api/auth/register` |
| **ヘッダ** | `Content-Type: application/json` など |
| **ボディ** | `{"email": "...", "password": "...", "birthday": "..."}` |

### ルーティングとは

**「どのURL（メソッド）が来たら、どの関数を実行するか」のマッピング**。Eien の `main.go` ではこう書いてある:

```go
e.POST("/api/auth/register", authHandler.Register)
e.POST("/api/auth/login",    authHandler.Login)
```

これは Echo に「POST /api/auth/register が来たら `authHandler.Register` を呼んでね」と教えている。郵便局の仕分け係のような役割。

### ハンドラ関数とは

ルーティングで指定された、リクエストを実際に処理する関数。3ステップを担う:

1. **リクエストから情報を取り出す**（`c.Bind(&req)`）
2. **ビジネスロジックを実行**（DB操作、バリデーション、ハッシュ化など）
3. **レスポンスを返す**（`c.JSON(...)`）

## 2. データアクセス層の選択肢

Go から DB にアクセスする方法には3つの流派がある。

| 流派 | 例 | 書き方 | 透明性 | 型安全 |
| --- | --- | --- | --- | --- |
| **生SQL派** | sqlc / database/sql 手書き | SQL直接 | ◎ | ◎ (sqlc) / △ (手書き) |
| **クエリビルダ派** | squirrel | Goコードで組み立て | △ | △ |
| **ORM派** | GORM, ent, bun | オブジェクト操作 | × | ◎ |

### sqlc の独自ポジション

> **「手書きSQLの透明性」と「ORMの便利さ・型安全性」の両取り**

sqlc は SQL ファイルを書くと、それを解析して**型付きの Go コード**を自動生成する。

```sql
-- queries/users.sql
-- name: GetUserByID :one
SELECT id, email FROM users WHERE id = $1;
```

↓ `sqlc generate` で自動生成

```go
user, err := queries.GetUserByID(ctx, userID)
// user は型付き構造体、コンパイル時に型エラーを捕捉
```

### N+1 問題（ORM で起こりやすい）

**N+1問題**：ループの中でクエリを呼び出すと、1件取得 + N件分の追加クエリ、で合計 N+1 回のクエリが発行される非効率な状態。

```go
// ❌ N+1 (ORM でやりがち)
groups := db.Find(&groups)  // 1回のクエリ
for _, g := range groups {
    members := db.Where("group_id = ?", g.ID).Find(&members)  // N回のクエリ
}

// ✅ JOINで1回のクエリ (sqlcなら明示的に書ける)
SELECT g.*, m.*
FROM groups g
LEFT JOIN group_members m ON m.group_id = g.id
```

sqlc を選ぶ強い理由の一つは、**N+1 問題に気づきやすい**こと。書いた SQL がそのまま実行されるので、非効率なクエリは目に見える。

## 3. パスワードハッシュ（bcrypt）

### なぜハッシュが必要か

- 平文保存：DBが漏洩したら全パスワードがバレる
- ハッシュ化：ハッシュから元のパスワードは復元できない（一方向関数）

### bcrypt の3つの特徴

| 特徴 | 内容 |
| --- | --- |
| **意図的に遅い** | 計算を繰り返すので、攻撃者の総当たりも遅くなる |
| **ソルトの自動付与** | 同じパスワードでも毎回異なるハッシュ。レインボーテーブル攻撃を無効化 |
| **コストパラメータ** | `Cost` 値で計算量を調整。ハードウェアが進化したらコストを上げる |

### なぜ SHA256 や MD5 ではダメか

- SHA256 / MD5 は**速いハッシュ**を目指して設計されている
- データの整合性チェック用途には適するが、**パスワード保存には不適**
- 速い = 攻撃者の総当たりも速い

### Argon2 / scrypt との比較

| ハッシュ関数 | 登場年 | 評価 |
| --- | --- | --- |
| **bcrypt** | 1999 | 古いが実績豊富。今でも十分安全 |
| **scrypt** | 2009 | メモリ消費型。GPU攻撃に強い |
| **Argon2** | 2015 | コンペ優勝。最新の推奨 |

## 4. 認証戦略：セッションベース vs JWT

### 比較表

| 観点 | セッションベース | JWT |
| --- | --- | --- |
| **状態の持ち場所** | サーバー（DBの `sessions` テーブル） | クライアント（JWT 自身に情報） |
| **stateful/stateless** | stateful | stateless |
| **確認方法** | Cookie の session_id → DB で照合 | 署名検証のみ |
| **ログアウト** | ✅ DBから削除で即無効化 | ❌ 有効期限まで止められない |
| **強制無効化** | ✅ 即可能 | ❌ 困難（ブラックリスト等が必要） |
| **保存場所** | HttpOnly Cookie | localStorage / Cookie |
| **CSRF対策** | 必要（SameSite / CSRFトークンで対処） | Authorization ヘッダなら不要 |
| **XSS耐性** | HttpOnly で JavaScript からアクセス不可 | localStorage は XSS で盗まれる |

### Eien がセッションベースを選んだ理由（README に絞った3つ）

1. **HttpOnly Cookie によるセキュリティ**（XSS対策）
2. **即時の無効化が可能**（ログアウト・強制ログアウト）
3. **標準的な CSRF 対策が利用可能**（SameSite + Echo の CSRF ミドルウェア）

### JWT のログアウト問題

JWT は「**サーバーが何も覚えていない**」のがメリットだが、ログアウトや強制無効化が必要になると:

| 対策 | 内容 | 問題 |
| --- | --- | --- |
| **短い有効期限** | 15分などで切る | UX悪い |
| **リフレッシュトークン** | 2段構成 | 設計複雑 |
| **ブラックリスト** | 無効化済みJWTのリスト | **statelessのメリット消滅** |

結局、ログアウトを真面目に実装すると JWT もサーバー状態管理が必要になり、セッションベースとの差が薄れる。

### CSRF と XSS（セキュリティ用語）

| 攻撃 | 内容 | 対策 |
| --- | --- | --- |
| **XSS**（Cross-Site Scripting） | 悪意のあるJSがページに混入してデータを盗む | HttpOnly Cookie / 出力エスケープ / CSP |
| **CSRF**（Cross-Site Request Forgery） | ログイン済みユーザーに偽サイトから認証付きリクエストを送らせる | SameSite Cookie / CSRFトークン |

## 5. DBマイグレーションと複数台運用

### マイグレーションとは

**DBのスキーマ（テーブル構造）の変更を、コードと同じように"履歴管理"する仕組み**。

```
db/migrations/
├── 001_create_users.up.sql      ← 適用 (CREATE TABLE)
├── 001_create_users.down.sql    ← ロールバック (DROP TABLE)
├── 002_create_sessions.up.sql
...
```

マイグレーションツール（golang-migrate）が:

- ファイルを順番に実行
- 「どこまで適用済みか」を `schema_migrations` テーブルで記録
- 既に適用済みのものは飛ばす

### マイグレーションの3つの効用

1. **環境間のスキーマ同期**（ローカル / ステージング / 本番）
2. **スキーマ変更の履歴が Git で追える**
3. **ロールバック可能**

### 起動時自動マイグレーションと複数台運用の問題

Eien は `main.go` の起動時にマイグレーションを自動実行する設計。**単一インスタンス前提**だからOK。

**複数台運用にすると問題が起きる:**

```
[サーバー#1 起動] → マイグレーション実行開始 ─┐
[サーバー#2 起動] → マイグレーション実行開始 ─┼ 同時に走る!
[サーバー#3 起動] → マイグレーション実行開始 ─┘
                       ↓
            DBで「CREATE TABLE が同時実行」される
                       ↓
            ❌ レースコンディション
```

**対策（複数台運用時）:**

- マイグレーション専用コマンドをデプロイ前に1回だけ実行
- PostgreSQL のアドバイザリーロックで多重実行を防ぐ

### 複数台運用（horizontal scaling）とは

**同じアプリを複数のサーバーで同時に動かす運用形態**。

```
シングル運用:
[User] → [Server #1] → [DB]

マルチ運用:
[User] → [Load Balancer] ─→ [Server #1] ─┐
                          ├→ [Server #2] ─┼→ [共有 DB]
                          └→ [Server #3] ─┘
```

**メリット:**

- **負荷分散**：1台では捌けない量を複数台で処理
- **冗長性**：1台落ちても他が生きている
- **無停止デプロイ**：1台ずつ順番に更新

**注意点:**

- 状態を持つ処理（マイグレーション、セッション、ファイル保存）を複数台で共有する設計が必要
- Eien は現状 `min_machines_running = 1` の単一インスタンス運用

## 6. React のデータフェッチと TanStack Query

素の `fetch + useEffect` で API を呼ぶと**5つの典型的な問題**が発生する。

### 問題①：キャッシュがない

```
タイムライン画面を開く → /api/timeline 取得
↓
投稿詳細画面に移動
↓
タイムラインに戻る → また /api/timeline を叩く！
```

家で例えると：冷蔵庫に牛乳があるのに毎回コンビニに買いに行く。

### 問題②：N+1 リクエスト（同じデータの重複取得）

ヘッダーで `/api/auth/me`、サイドバーでも `/api/auth/me`。同じデータなのに2回叩く。

家で例えると：兄と弟が母に同じ質問を別々に聞く。

### 問題③：ローディング/エラー状態を毎回手で書く

```tsx
const [data, setData] = useState(null);
const [loading, setLoading] = useState(true);
const [error, setError] = useState(null);
// ... 毎回これを書く
```

### 問題④：タブ切り替えで古いデータ

朝開いたタイムラインを、夕方タブに戻っても朝のデータが表示されたまま。

### 問題⑤：競合状態（race condition）

```
17:00:00.000  ユーザー「a」入力 → /api/search?q=a を叩く（リクエストA）
17:00:00.500  ユーザー「ab」入力 → /api/search?q=ab を叩く（リクエストB）
17:00:00.800  リクエストB が戻ってきた → 画面に「ab の結果」
17:00:01.200  リクエストA が遅れて戻ってきた → 画面に「a の結果」を上書き！
```

最終表示は「a」の結果だが、ユーザーが最後に入力したのは「ab」。

### TanStack Query の対処

| 問題 | TanStack Query の対処 |
| --- | --- |
| ① キャッシュなし | 自動キャッシュ（queryKey で識別） |
| ② 重複取得 | 同じキーは1回しか叩かない |
| ③ ローディング状態 | `isLoading`, `error`, `data` 標準搭載 |
| ④ タブ切り替え時の古さ | 自動 refetch |
| ⑤ 競合状態 | 古いリクエストは破棄 |

### 使い方の最小例

```tsx
function PostList() {
  const { data: posts, isLoading, error } = useQuery({
    queryKey: ['posts'],
    queryFn: () => fetch('/api/posts').then(r => r.json()),
  });

  if (isLoading) return <p>Loading...</p>;
  if (error) return <p>Error</p>;
  return <ul>{posts.map(p => <li key={p.id}>{p.title}</li>)}</ul>;
}
```

## 7. Vite の高速性（HMR / esbuild）

Vite の「変更が即反映される」は2つの技術によるもの:

| 観点 | Vite | Webpack（旧来） |
| --- | --- | --- |
| **開発サーバー起動** | 即座（ネイティブESMを使用） | 全コードバンドル後 → 遅い |
| **変更時の反映** | 変更ファイルだけ更新（HMR） | 全体再バンドル → 遅い |
| **トランスパイラ** | esbuild（Go製・高速） | Babel（JS製・遅い） |

### HMR（Hot Module Replacement）

ファイルを保存すると、**変更されたモジュールだけ**がブラウザに送られて差し替わる。ページ全体のリロード不要。

### esbuild

Vite が使うトランスパイラ（TypeScript → JavaScript の変換など）。**Go 製**で、JavaScript 製の Babel より**10〜100倍速い**。

### Create React App はもう使わない

2025年初頭にメンテナンス終了。**新規プロジェクトでは Vite が事実上の標準**。

## 8. インフラ・デプロイ

### Fly.io の位置付け

| サービス | 特徴 |
| --- | --- |
| **Fly.io** | Docker をそのままデプロイ。Heroku 後継的存在。東京リージョンあり |
| **AWS** | 業界トップシェア。自由度高、学習コスト大 |
| **Heroku** | 老舗だが、日本リージョンなし、無料枠廃止 |
| **Vercel** | フロント特化（Next.js等）、Goバックエンドには不向き |

Fly.io は「**PaaS と IaaS の中間**」。Heroku より自由度が高く、AWS より設定が少ない。学習プロジェクトに最適。

### Docker マルチステージビルドの意義

Eien の Dockerfile は3段階:

- **Stage 1**：フロント（Node + Vite）をビルドし、`dist/` を生成
- **Stage 2**：バック（Go）をビルドし、シングルバイナリを生成
- **Stage 3**：軽量 Alpine ベースの最終イメージに、上記2つの成果物のみコピー

これにより、最終イメージには Go / Node のビルドツールチェーンが含まれず、**イメージサイズが最小化**。デプロイ速度・コールドスタート時間・セキュリティ表面積すべてで利点。

## 9. 言語選定の判断軸

### Go vs Node vs Python（バックエンド）

| 軸 | Go | Node.js | Python |
| --- | --- | --- | --- |
| **型** | 静的・強い | 動的（TS で補強） | 動的（型ヒントは緩い） |
| **実行性能** | コンパイル・高速 | 速い | 遅い（インタプリタ） |
| **並行処理** | goroutine（言語標準） | イベントループ（シングルスレッド） | GIL制約あり |
| **学習リソース** | Tour of Go等 | 膨大 | 膨大 |

### Eien が Go を選んだ理由（README 採用版）

- 学習リソースの充実（Tour of Go）
- シンプルな文法
- goroutine による並行処理
- 就職市場での評価

### TypeScript の価値

**バックエンドで Go を選んだ理由と同じ価値観**：型安全な開発体験を、フロントエンド・バックエンド双方で揃えたかった。

### 「学習投資の配分」というキーフレーズ

Eien では、**フロントエンドは既知技術（React + Tailwind）で固定**して、**新規挑戦をバックエンド・インフラに集中**させた。これは **プロジェクトマネジメント的な判断**で、面接で評価されるキーフレーズ。

「全部新しい技術で挑戦しました」よりも、「**学習投資の配分を考えました**」の方がプロ寄りに聞こえる。
