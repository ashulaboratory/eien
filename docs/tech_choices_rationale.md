# 技術選定の判断記録

本ドキュメントは、Eien の各技術選定について、採用理由・代替案を採用しなかった理由を詳細に記録するものです。README には選定の要約を載せていますが、本ドキュメントでは選定プロセスを技術ごとに掘り下げています。

---

## 選定の流れ

本プロジェクトの個人的な学習動機は「初めてのバックエンド開発に取り組み、フロントエンドからバックエンド、データベース、インフラまでフルスタックで設計・実装できる状態を作る」ことだった。フロントエンドは既に経験があったため、新規挑戦の中心はバックエンド側（言語・フレームワーク・データアクセス・認証・デプロイ）に置いている。

そのため技術選定はバックエンド側から開始した。最初に Go を「初めてのバックエンド言語」として選び、それを起点に Web フレームワーク（Echo）や認証実装（bcrypt + セッション）が決まっていった。バックエンドの整理がついた段階でデータベース（PostgreSQL）を選び、それに連鎖してデータアクセス層（sqlc + pgx）とマイグレーションツール（golang-migrate）が連動して決まった。フロントエンドは経験のある React を中心に組み、最後にインフラ・デプロイ層を選定した。以下に各レイヤーの選定理由を示す。

---

## バックエンド

### 言語：Go

**比較した代替案:** Node.js (TypeScript) / Python (FastAPI 等) / Ruby (Rails) / Rust / Java (Kotlin) 等

**Go を採用した理由:**

- **未経験の言語として学習機会を最大化できる**：本プロジェクトの言語選定は、「触ったことのない、バックエンドで広く採用されている言語を1つ習得する」という学習動機が出発点だった。研究・業務で既に経験のある Python ではなく、未経験の言語を学ぶ方が学習効果が高いと判断した。
- **学習者にとって分かりやすい言語特性**：クラス継承や例外などの複雑な言語機能が少なく、シンプルな文法を持つ。バックエンド自体が初挑戦の本プロジェクトでは、言語側でつまずく時間を最小化し、バックエンドの基礎概念（HTTP / DB / 認証）の理解に集中したかった。
- **学習リソースの充実**：公式の "A Tour of Go" など段階的な学習資料が整っており、独学の見通しが立てやすい。
- **言語レベルの並行処理サポート**：goroutine / channel を備え、Web サーバー実装に向いた言語特性を持つ。
- **就職市場での採用実績**：バックエンド・インフラ系の現場で広く採用されており、学習投資の回収が見込める。

**他言語を採用しなかった理由:**

- **Node.js**：フロントエンド（TypeScript）と同じ言語になるため、本プロジェクトの学習動機（未経験言語の習得）を満たせない。フロントとは異なる言語・パラダイムに触れる方が得られるものが大きいと判断した。
- **Python**：研究・業務で継続的に書いてきた経験があり、本プロジェクトの学習動機（未経験の backend 言語を1つ習得する）には合致しなかった。Python と Go では型システムや並行処理モデル、デプロイ形態などに違いはあるが、選定の決め手は「自分にとって未経験の言語であること」だった。
- **Ruby (Rails) / Rust / Java (Kotlin) など**：未経験言語の他の候補。本プロジェクトでは「初学者にとっての分かりやすさ」を重視した時点で Go に絞り込み、これらとの詳細比較は行わなかった。本プロジェクトの規模ではいずれの言語でも要件を満たせる前提があり、複数言語の比較検証より、選んだ言語を深く学ぶ方を優先した。

### Web フレームワーク：Echo v4

**比較した代替案:** Gin / `net/http`（標準ライブラリ）

**選定の経緯:**

正直なところ、Echo と Gin の詳細な比較検討は当時行わなかった。Web フレームワーク自体に不慣れな状態だったため、まず Echo に手をつけて、ルーティング・ミドルウェア・リクエストバインディング・Cookie 操作など本プロジェクトに必要な機能が一通り賄えることを確認した時点で選定を確定させた。

**振り返り:**

GitHub の star 数や StackOverflow の総量で見ると Gin の方が情報量は多く、本プロジェクトの規模・要件（小規模な認証付き SPA + バッチ）であれば Gin でも問題なく実装できたと振り返っている。Echo で実装を進める中で書き味（特に `e.Group("/api", authMiddleware)` でのグループへのミドルウェア適用）に不満はなかったため、選定自体に問題はなかったが、「**Echo が Gin より優れているから選んだ**」と主張できる強い根拠はなく、**当時の選定プロセスとしては『深く比較せず、最初に手をつけた方で進めた』が事実**である。

**net/http（標準ライブラリ）を採用しなかった理由:**

ルーティング・ミドルウェア・リクエスト処理を自前で組む必要があり、Web フレームワーク自体の理解が浅い段階で並行して学ぶには学習コストが大きい。「Web フレームワークが何をやってくれているか」を Echo の上で理解した後で、必要に応じて標準ライブラリでも組めるようになる方が学習効率が良いと判断した。

### 認証ハッシュ：bcrypt

**比較した代替案:** SHA256 / scrypt / Argon2

**bcrypt を採用した理由:**

- **総当たり攻撃への耐性**：意図的に処理が遅いハッシュ関数として設計されており、攻撃者がパスワードを総当たりで試行する難易度が上がる。SHA256 などの高速ハッシュ関数はパスワード保存用途には不適。
- **ソルトの自動組み込み**：bcrypt は内部でソルトを自動で付与するため、同じパスワードでも毎回異なるハッシュが生成される。レインボーテーブル攻撃を無効化できる。
- **API がシンプルで取り回しやすい**：`bcrypt.GenerateFromPassword` と `bcrypt.CompareHashAndPassword` の2関数だけでハッシュ化・検証が完結する。ソルトの生成やエンコードは内部で処理される。

**他のハッシュ関数を採用しなかった理由:**

- **SHA256 / MD5 など**：高速ハッシュ関数は整合性チェック用途には適するが、パスワード保存には不向き。
- **Argon2 / scrypt**：いずれも bcrypt より新しいハッシュ関数で、現代の推奨は Argon2 寄りである点は認識している。一方で、bcrypt は `golang.org/x/crypto/bcrypt`（Go 公式メンテのパッケージ）から上述のシンプルな API で利用できるため、本プロジェクトの規模・脅威モデル（個人開発・小規模利用）では bcrypt の取り回しの良さを優先した。

**Cost パラメータについて:**

bcrypt は Cost パラメータで計算量（2 の Cost 乗）を調整でき、ハードウェアの高速化に対しても将来的に Cost を引き上げて対応できる設計になっている。本プロジェクトでは標準値（`bcrypt.DefaultCost` = 10）で運用している。

### 認証戦略：セッションベース認証

**比較した代替案:** JWT（JSON Web Token）認証

**セッションベースを採用した理由:**

- **HttpOnly Cookie によるセキュリティ**：セッションID を HttpOnly Cookie に格納することで、JavaScript からアクセスできない状態にできる。XSS（クロスサイトスクリプティング）攻撃でセッションIDが盗まれるリスクを低減できる。
- **即時の無効化が可能**：DB の `sessions` テーブルからレコードを削除するだけで、対象セッションを即座に無効化できる。ログアウトや、漏洩時の強制ログアウトに対応しやすい。
- **標準的な CSRF 対策が利用可能**：Cookie ベースの認証では CSRF（クロスサイトリクエストフォージェリ）への対策が必要になるが、SameSite Cookie 属性と Web フレームワークの CSRF ミドルウェアの組み合わせで標準的に対処できる。

**JWT を採用しなかった理由:**

- **ログアウト・強制無効化が困難**：JWT は発行後、有効期限が切れるまで強制的に無効化する仕組みが標準では用意されていない。ブラックリスト管理を追加するとサーバー側の状態管理が必要になり、JWT の "stateless" というメリットが薄れる。
- **本プロジェクトの規模では恩恵が小さい**：JWT の主なメリットはマイクロサービス間認証やモバイル・複数台展開などで活きる。本プロジェクトの構成（React SPA + 単一インスタンスのバックエンド）には該当しない。

### 定期実行：robfig/cron

誕生日通知などの定期処理を実装するために採用した、Go 界隈で定番のスケジューラライブラリ。

- **cron 形式の表現でジョブを書ける**（例: `0 9 * * *` で毎日朝9時実行）ため、可読性が高い。
- 別プロセスのバッチジョブとして切り出す選択肢もあったが、Fly.io 上で**常駐プロセス1つで完結させたい**ため、アプリ内スケジューラを選んだ。
- 開発時の手動実行用に `cmd/birthday/main.go` という別エントリポイントも用意しており、ジョブのデバッグや単発実行ができる構成にしている。

### ID 生成：google/uuid

UUID v4 を生成する標準的なライブラリ。Google が公開しており、Go 界隈で広く採用されている。テーブルの主キーや招待トークンなどの一意な識別子の生成に利用。

## データベース・データアクセス層

バックエンドの言語・フレームワークが Go + Echo に決まった段階で、Go から扱う前提でデータベース層を選定した。まず DB として PostgreSQL を採用し、**その結果として**データアクセス層（sqlc + pgx）やマイグレーションツール（golang-migrate）の選定が連鎖的に決まっていった。

### データベース：PostgreSQL 16

**比較した代替案:** MySQL / SQLite / MongoDB

**PostgreSQL を採用した理由:**

- **機能の豊富さ**：UUID、JSON、配列など、PostgreSQL がネイティブで提供する機能が充実している。Eien のように UUID を主キーに使うサービスとは特に相性が良い。
- **学習価値の高さ**：業界の主要プロジェクトでの採用実績が広く、PostgreSQL に習熟することは将来的なキャリアにも活きる。
- **デプロイ先（Fly.io）との相性**：Fly.io は PostgreSQL のホスティングを公式にサポートしており、別途 DB サービスを契約する必要がなく、運用がシンプルになる。

**他のデータベースを採用しなかった理由:**

- **MySQL**：採用シェアは高いが、PostgreSQL に比べて機能（特に JSON、UUID、配列等のネイティブ型）の点で見劣りする。学習投資先として PostgreSQL を優先した。
- **SQLite**：軽量で単一ファイル運用が可能だが、複数台運用や同時書き込みへの対応が弱く、本番採用は避けた。
- **MongoDB**：NoSQL データベース。Eien のデータモデル（ユーザー / グループ / 投稿 / メンバー といった明確な関係を持つもの）には、RDB のリレーショナルモデルが自然。

### データアクセス層：sqlc + pgx

**比較した代替案:** 手書き SQL（`database/sql`） / クエリビルダ（squirrel） / ORM（GORM 等）

**sqlc を採用した理由:**

- **SQL の透明性を保ちたい**：ORM の裏側で発行されるクエリが見えづらくなる状態を避けたかった。学習段階として、自分が書いた SQL がそのまま実行される構造が望ましいと判断した。
- **型安全性を確保したい**：sqlc は SQL を解析して型付きの Go コードを自動生成するため、コンパイル時にミスを検出できる。手書き SQL のように `Scan` のカラム数ズレが実行時まで残らない。

**他の選択肢を採用しなかった理由:**

- **手書き SQL**：透明性は最大だが、`Scan` の整合性が実行時まで検証されず、ボイラープレートも多い。
- **ORM（GORM）**：抽象化が強く、裏で発行されるクエリが見えづらい。N+1 問題などのパフォーマンス課題に気づきにくくなる懸念があった。

**pgx の採用:**

PostgreSQL ドライバとして `pgx` v5 を採用。sqlc が pgx 向けのコード生成モードに対応しており、生成コードが pgx の機能（PostgreSQL ネイティブ型のサポート等）をそのまま活用できる構成になっている。

### マイグレーション：golang-migrate

**比較した代替案:** goose / Atlas / ORM 内蔵マイグレーション

**採用した理由:**

- **採用実績の広さ**：Go 界隈で最も広く使われているマイグレーションツールで、ドキュメント・トラブルシューティング情報が豊富。学習プロジェクトとしてつまずきにくい。
- **ORM 非依存**：sqlc を採用しているため、ORM 内蔵のマイグレーション機能は選択肢に入らない。独立した SQL ベースのマイグレーションツールが必要だった。

**起動時の自動マイグレーションについて:**

`main.go` の起動シーケンスで未適用のマイグレーションを自動実行している。Fly.io へのデプロイ後に別途マイグレーションコマンドを実行する必要がなく、デプロイフローがシンプルになる。単一インスタンス運用を前提とした選択であり、複数インスタンス化する際は別途マイグレーション専用ジョブを切り出す設計に変更する必要がある。

## フロントエンド

### UI ライブラリ：React 19

**比較した代替案:** Vue.js / Svelte / Next.js

**React を採用した理由:**

- **既に経験があり、学習コストを抑えられる**：本プロジェクトでは新規挑戦（バックエンド・インフラ・データモデリング）に学習リソースを集中させたかったため、フロントエンドは既に経験のある React を採用した。
- **本プロジェクトの要件を満たすのに機能面で不足がない**：認証付き SPA に必要な UI 構成、状態管理、ルーティング・データフェッチライブラリ（React Router / TanStack Query 等）との統合など、Eien に必要な範囲は React で十分にカバーできる。

**他のライブラリを採用しなかった理由:**

- **Vue.js / Svelte**：それぞれ書き味やパフォーマンス面での評価はあるが、本プロジェクトでは「既に経験のある技術を選んで他の層に学習を集中する」という方針を優先し、新たに学び直す必要のない React を選んだ。
- **Next.js**：React の上位フレームワークで、SSR・ルーティング・API 等を統合的に提供する。ただし本プロジェクトはバックエンドを Go で別途構築する構成のため、Next.js のフルスタック機能は不要。

### 言語：TypeScript

**比較した代替案:** 素の JavaScript

**TypeScript を採用した理由:**

- **静的な型チェックで安全性が高い**：型を明示することで、変数や関数の入出力の不整合を実行前に検出できる。バックエンドで Go を採用した理由と同じ価値観で、フロントエンド・バックエンド双方で型安全な開発体験を揃えたかった。
- **React エコシステムでの採用が広い**：主要なライブラリ（React, React Router, TanStack Query 等）が TypeScript ファーストで型定義を提供しており、エコシステム全体で型安全な開発がしやすい。

### ビルドツール：Vite

**比較した代替案:** Create React App / Webpack 手動設定

**Vite を採用した理由:**

- **開発時の反映が高速**：ネイティブ ES Modules を活用し、コード変更が即座にブラウザに反映される（HMR / Hot Module Replacement）。Webpack ベースのツールに比べて開発サイクルが大幅に速くなる。
- **現代の React 開発における事実上の標準**：従来主流だった Create React App は 2025年初頭にメンテナンスが終了しており、新規プロジェクトでは Vite が事実上の標準となっている。

### スタイリング：Tailwind CSS v4

**比較した代替案:** CSS Modules / styled-components / 素のCSS・SCSS

**Tailwind CSS を採用した理由:**

- **既に経験があり、学習コストを抑えられる**：React と同様、フロントエンドの基礎部分は既知の技術で固定し、新規挑戦を他の層に集中させる方針に従った。
- **ユーティリティクラスによる素早い実装**：`p-4 bg-blue-500 rounded` のようにクラスを組み合わせるだけでスタイリングが完結する。クラス命名やCSSファイル管理の悩みから解放され、UI 実装に集中できる。

**他のスタイリング手段を採用しなかった理由:**

- **CSS Modules / styled-components / 素のCSS**：いずれもクラス命名・スコープ管理の負担が Tailwind より大きく、本プロジェクトの規模では恩恵が薄かった。

### データフェッチ：TanStack Query (React Query)

**比較した代替案:** 素の `fetch` + `useEffect` / SWR / Redux Toolkit Query

**TanStack Query を採用した理由:**

素の `fetch` + `useEffect` の構成では、データ取得まわりで複数の典型的な問題が発生する。

- **API のキャッシュがない**：同じデータを画面遷移のたびに再取得してしまい、無駄なリクエストが増える。
- **同じデータを別コンポーネントで重複取得する**：複数コンポーネントが同じエンドポイントを別々にフェッチし、N+1 リクエストになる。
- **ローディング/エラー状態を毎回手書きする**：`useState` による状態管理を毎回繰り返す必要があり、コードが冗長になる。
- **古いデータがそのまま表示される**：ユーザーがタブを離れて戻ってきた時、データの再フェッチが行われず古いデータが表示され続ける。
- **競合状態（race condition）**：古いリクエストの結果が新しいリクエストの結果を上書きしてしまう可能性がある。

TanStack Query は上記の問題に対し、**キャッシュ管理・状態管理・自動再フェッチ・古いリクエストの破棄**を標準で備えており、最小のコードで安全なデータ取得を実装できる。

**他の代替案を採用しなかった理由:**

- **素の fetch + useEffect**：上記の典型的な問題を全て自前で解決する必要があり、コード量・バグの発生リスクが大きい。
- **SWR / Redux Toolkit Query**：TanStack Query と似た目的のライブラリだが、機能の豊富さとドキュメント・コミュニティの厚さで TanStack Query を優先した。

### ルーティング：React Router 7

**比較した代替案:** TanStack Router / wouter

**React Router を採用した理由:**

- **採用実績と学習リソースの厚み**：React 開発で最も広く採用されているルーティングライブラリで、ドキュメント・解説記事・トラブルシューティング情報が充実している。
- **本プロジェクトで活用しているネスト構造**：認証チェック（`ProtectedRoute`）と共通レイアウト（`Layout`）を親ルートに集約し、その下に複数のページを子ルートとして配置できる。各ページで認証チェックや UI 枠を重複して書く必要がなく、構造を整理しやすい。

  ```tsx
  <Route element={<ProtectedRoute />}>     {/* 認証チェックを集約 */}
    <Route element={<Layout />}>           {/* 共通UI枠を集約 */}
      <Route path="/" element={<Timeline />} />
      <Route path="/groups" element={<Groups />} />
      ...
    </Route>
  </Route>
  ```

**他のルーティングライブラリを採用しなかった理由:**

- **TanStack Router / wouter**：いずれも候補に挙がったが、React Router で本プロジェクトに必要なネスト構造・認証付きルート・動的パラメータ（`/groups/:id`）が満たせる見通しが立った時点で選定を確定させ、詳細比較は行わなかった。

## インフラ・デプロイ

### デプロイ先：Fly.io

**比較した代替案:** AWS / Heroku / Vercel

**Fly.io を採用した理由:**

- **Docker イメージをそのままデプロイできる手軽さ**：`fly deploy` 一つで、ローカルでビルドした Docker イメージが本番に反映される。CI/CD パイプラインや構成ファイルの細かい調整なしに本番デプロイまで到達できるため、学習プロジェクトに適している。
- **東京リージョン (nrt) を選択可能**：国内ユーザーへの低レイテンシを確保できる。
- **料金体系がシンプル・小規模なら低コスト**：常駐インスタンス1台 + PostgreSQL の最小構成で運用でき、学習プロジェクトの予算規模に合う。
- **PostgreSQL の公式サポート**：データベースのホスティングを Fly.io 内で完結でき、運用面のシンプルさに繋がる。

**他のデプロイ先を採用しなかった理由:**

- **AWS (ECS/EC2)**：自由度は最大だが、IAM / VPC / ロードバランサ等の構成要素が多く、学習コストが本プロジェクトの主目的（フルスタック開発の経験）から外れる。
- **Heroku**：かつての定番だが、無料枠廃止と日本リージョンの欠如により採用候補から外した。
- **Vercel**：フロントエンドホスティングに特化しており、Go バックエンドをサーバーレスで動かす構成は本プロジェクトのコンテナベース運用方針と合わない。

### コンテナ：Docker（マルチステージビルド）

**採用理由:**

- **デプロイ先（Fly.io）との適合**：Fly.io は Docker イメージを単位としてデプロイする設計のため、Docker による標準的なコンテナ化が必須。
- **ローカル開発と本番環境の差異を最小化**：`docker compose` でローカルでも PostgreSQL + Mailhog を立ち上げる構成にしており、ローカルと本番でアプリの動作環境を揃えやすい。

**マルチステージビルドを採用した理由:**

`backend/Dockerfile` は3段階のマルチステージビルドを採用している。

- **Stage 1**：フロントエンド（Node + Vite）をビルドし、`dist/` を生成
- **Stage 2**：バックエンド（Go）をビルドし、シングルバイナリを生成
- **Stage 3**：軽量な Alpine ベースの最終イメージに、上記2つの成果物のみをコピー

これにより、最終本番イメージには Go / Node のビルドツールチェーンが含まれず、**イメージサイズが最小化**される。デプロイ速度・コールドスタート時間・セキュリティ表面積のすべてで利点がある。

### 画像ストレージ：開発 = ローカルディスク / 本番 = Cloudflare R2

**開発時：ローカルディスク**

開発時は `backend/uploads/` 配下に保存し、バックエンドの `/uploads` 静的配信エンドポイント経由で参照する。Git の追跡対象外で、ローカル開発の手軽さを優先した構成。

**本番：Cloudflare R2**

本番では Cloudflare R2 を採用する。

- **S3 互換 API**：S3 向けのライブラリ・ツールチェーンがそのまま利用できる。
- **エグレス料金が無料**：オブジェクトストレージから外向きへのデータ転送が無料で、画像配信を含む SNS の典型的なアクセスパターンと相性が良い。
- **個人開発の予算規模に合う**：無料枠（保存容量 10 GB）が用意されており、Eien の現状想定では追加コストが発生しにくい。

**実装上の抽象化:**

`backend/internal/post/storage.go` の `ImageStore` インターフェースを介して画像保存・取得を抽象化しており、本番化は `LocalImageStore` を `R2ImageStore`（未実装、後続タスク）に差し替えるだけで完了する設計。

```go
type ImageStore interface {
    Save(ctx context.Context, content io.Reader, contentType string) (publicURL string, err error)
}
```

なお、Fly.io のインスタンス再起動でローカルディスクの内容は失われるため、本番リリース前にこの差し替えが**必須**となる。

### メール送信：開発 = Mailhog / 本番 = Resend

**開発時：Mailhog**

誕生日通知メール等の挙動を、開発時にローカルで安全に確認するために採用。本物のメールアドレスには送信されず、Mailhog の Web UI（`http://localhost:8025`）で送信内容を可視化できる。

**本番：Resend**

本番では Resend を採用する。

- **無料枠が個人開発の規模に合う**：月 3,000 通までの無料枠があり、Eien の現状想定（小規模グループ、誕生日通知が中心）には十分。
- **開発者体験が良い**：SPF / DKIM などのドメイン認証設定がダッシュボード上で完結する。
- **他候補との比較**：SendGrid は無料枠の縮小傾向、AWS SES は配送品質を担保するための設定コストが大きいため、本プロジェクトの規模・運用負荷の観点で Resend を優先した。

`backend/internal/notification/mailer.go` の SMTP 設定を差し替えるだけで本番への切り替えが行える構成にしている。
