## 1. 自己紹介・プロジェクト概要

### Q1-1. このプロジェクトについて1分で説明してください。

> **Eien（エイエン）という招待制のクローズドSNSを個人開発しました。**
> 部活・家族・サークルなど、信頼できる人だけの場で「人生の節目」を共有するためのアプリです。
> 大きな特徴は2つあって、(1) 1アカウントで複数グループに所属しつつ、グループごとに表示名を切り替えられること、(2) 誕生日トリガーでメール通知が飛び、当日アプリ内で豪華表示になることです。
> 技術スタックはフロント React + TypeScript + Vite、バックエンドが Go の Echo フレームワーク、DB が PostgreSQL、本番デプロイは Fly.io です。要件定義からデプロイまで一人で通しました。

**深掘りポイント**：「Eienらしさ＝既存SNSがやらないこと」を聞かれたら、「既存はオープン・拡散・フォロー数中心。Eienは閉じた場で深い関係に向ける設計」と答える。

---

### Q1-2. なぜこのテーマを作ろうと思ったんですか？

> 既存のSNSが「広く浅く」に最適化されていて、自分が大事にしている狭い人間関係には合わないと感じたのが出発点です。
> ただ動機より、要件定義 → 設計 → 実装 → デプロイまで一気通貫で経験することを優先したので、テーマは「自分が欲しいと思える最小のもの」を選びました。

---

### Q1-3. 開発期間と進め方を教えてください。

> 約1ヶ月で MVP まで持っていきました。
> 最初の数日で要件定義書（`docs/requirements.md`）を書いて MoSCoW で優先度を切り、その後 ER 図と API 設計を `docs/design.md` にまとめてから実装に入りました。
> 途中で「学習モード（理解を優先）」から「最速で公開モード」に切り替えた瞬間があり、それ以降は実装スピードが上がりました。

## 2. 技術選定の理由

### Q2-1. なぜ Go を選んだんですか？

> 3つあります。
> 1つめは**学習コストとパフォーマンスのバランス**。型があるのに構文が小さく、コンパイルが速く、本番の実行性能も出ます。
> 2つめは**標準ライブラリでWebサーバが書ける**こと。何が起きているか追いやすく、勉強目的に合っていました。
> 3つめは**シングルバイナリでデプロイできる**こと。Docker イメージが小さくなり、Fly.io の無料枠と相性が良いです。
>
> 比較対象は Node.js + Express でしたが、型をきちんと使いたかったのと、Go の goroutine ベースの並行処理に触れてみたかったのでこちらにしました。

**深掘り**：「Rust じゃダメだった？」→「学習曲線が急で、MVP までの期間に合いませんでした。Go は『そこそこ厳しいけど読める』バランスが良かったです」

---

### Q2-2. ORM ではなく sqlc を選んだ理由は？

> **SQL を自分で書きたかったからです。**
> GORM のような ORM だと裏で発行されるクエリが見えにくく、N+1 などの問題に気づきにくい。sqlc は SQL ファイルを書くと型安全な Go コードを生成してくれるので、「SQL の勉強になる」「実行されるクエリが完全に見える」「型エラーがコンパイル時に出る」の三拍子が揃っています。
>
> 限界もあって、動的に WHERE 句を組み立てるような複雑なクエリは苦手です。そういうケースは将来 squirrel などのクエリビルダを併用する想定です。

---

### Q2-3. なぜ React + Vite ？ Next.js じゃない理由は？

> Eien は SEO の必要がない（ログイン後のクローズド領域がほぼ全部）ので、SSR は不要でした。**SPA で十分**だったため、より薄くて起動の速い Vite を選びました。
> Next.js は機能が多すぎて学習コストが MVP に対して重く、選びませんでした。
> ただし、将来「招待リンクから来た未ログインユーザー向けのランディングページ」が必要になったら、Next.js への移行も視野に入ります。

---

### Q2-4. PostgreSQL を選んだ理由は？ MySQL じゃダメ？

> 3つ理由があります。
> (1) **UUID と JSONB を扱いやすい**。Eien は UUID を主キーにしているので相性が良い。
> (2) **マイグレーションのトランザクション対応が強い**。MySQL は DDL の途中で失敗するとロールバックできないことがあります。
> (3) Fly.io の **Postgres マネージドサービス**がそのまま使える。
>
> MySQL を否定しているわけではなく、規模・要件で十分入れ替え可能だと思います。

---

### Q2-5. Fly.io を選んだ理由は？ AWS や Vercel ではなく？

> 個人開発の MVP 段階で、**コストとシンプルさ**を最優先しました。
> Vercel はフロントには良いが Go のバックエンドを動かしにくい。AWS はフル機能だが学習コストが高くコスト事故のリスクもある。Fly.io は `fly deploy` 一発で東京リージョンに Docker イメージごとデプロイでき、Postgres も付属。Cron 用に常時稼働 1 マシン構成にできるのも、誕生日通知ジョブにマッチしました。

## 3. 認証・セキュリティ

### Q3-1. 認証はどう実装しましたか？

> **サーバ側セッション + Cookie** の方式です。
> ログイン成功時に CSPRNG で 32 バイト＝256bit のランダム ID を生成し、`sessions` テーブルに `(id, user_id, expires_at)` で保存します。クライアントにはこの ID を `session_id` という **HttpOnly Cookie** で返します。以降のリクエストは認証ミドルウェアが Cookie を見て DB と照合し、`userID` を `context` に格納してハンドラに渡す、という流れです。
> パスワードは bcrypt（cost 10）でハッシュ化して保存しています。

---

### Q3-2. なぜ JWT じゃなくてセッション方式？

> JWT は「ステートレスで横スケールしやすい」のが利点ですが、Eien 規模では DB を引く方式で何の問題もなく、むしろ **即時失効ができる**メリットの方が大きいと判断しました。
> JWT は一度発行すると有効期限内は失効できない（ブラックリスト持つと結局ステートフルになる）ので、ログアウトやセキュリティ事故対応の観点でセッションの方が運用しやすいです。
> 横スケールが必要になったら、セッションを Redis に逃がせばいいだけです。

---

### Q3-3. セキュリティで意識したことは？

> OWASP の Top 10 を意識して、最低限以下をやりました。
>
> - パスワード：bcrypt でハッシュ（cost 10、平文保存しない）
> - セッション Cookie：`HttpOnly` で JavaScript からアクセス不可、本番は `Secure` 有効化、`SameSite=Lax` で CSRF をある程度抑制
> - SQL インジェクション：sqlc がプレースホルダを必ず使うので原理的に発生しない
> - XSS：React の自動エスケープに依存、`dangerouslySetInnerHTML` を使わない
> - 認可：すべての投稿・グループ操作で「そのユーザーがメンバーか」を `IsGroupMember` クエリで確認してから操作
> - 招待トークン：CSPRNG で生成
>
> **やれていない / Phase 1 で入れる**：CSRF トークンの明示的検証（今は SameSite に依存）、ログイン試行のレート制限、画像 EXIF 削除、MFA。

**深掘りされたら正直に**：「Secure 属性は本番でしか効かないので、`Secure: false` を環境変数で切り替える実装になっていて、ここはまだ甘いです」

---

### Q3-4. パスワードはどうやって守ってる？

> bcrypt でハッシュ化して `password_hash` カラムに保存しています。bcrypt は **ソルト自動付与 + 計算量パラメータ（cost）でブルートフォース耐性を持つ**ハッシュ関数です。cost を 10 にしているので、1回のハッシュ計算に約 100ms かかります。
> もしハッシュ値がリークしても、レインボーテーブル攻撃はソルトで防げ、総当たりも cost で実用的でないコストにできます。

---

## 4. DB 設計

### Q4-1. テーブル構成を簡単に教えてください。

> 8テーブルです。
> `users` / `sessions` / `groups` / `group_members` / `invite_links` / `posts` / `post_images` / `email_logs`。
>
> 設計の肝は **`group_members` が「誰がどのグループに、どの表示名で所属しているか」を持つ中間テーブル**になっていることです。ユーザーが複数グループに別表示名で入れるのはこの設計から来ます。

---

### Q4-2. なぜ ID に UUID を使ったんですか？

> 3つ理由があります。
> (1) **URL を見て連番から件数を推測されない**（`/posts/12345` だと総数バレる）
> (2) **複数 DB / 分散環境で衝突しない**：将来の拡張に耐える
> (3) **クライアント側で先に ID を発行できる**：オフライン同期等に有利
>
> デメリットは bigint より重い（16 バイト vs 8 バイト）、インデックスがやや太る、ことです。Eien 規模では問題にならないので採用しました。

---

### Q4-3. インデックスはどう貼っていますか？

> 投稿テーブルなら `idx_posts_group_id_created_at ON posts(group_id, created_at DESC)` を貼っています。
> これは**タイムラインの主クエリ「あるグループの投稿を新しい順に取得」を高速化する複合インデックス**です。`created_at DESC` で並びまでインデックスに乗せているので、`ORDER BY` のコストがほぼゼロになります。
>
> sessions は `user_id` に、posts は `author_user_id` に index を貼っています。

---

### Q4-4. 投稿削除は物理削除？論理削除？

> **論理削除（soft delete）** にしています。`posts` テーブルに `deleted_at TIMESTAMPTZ` を持たせ、削除時はこのカラムに時刻を入れるだけ。クエリ側で `WHERE deleted_at IS NULL` を付けて取得から外しています。
> 理由は、(1) 誤削除のリカバリが効く、(2) 監査・分析が後からできる、(3) 関連する `post_images` を即座に消すと整合性が取りづらい、です。
> ただし物理削除を完全にやらないと GDPR 的にはまずいケースがあるので、将来は「30日後に物理削除するバッチ」を足したいです。

---

### Q4-5. N+1 問題は意識した？

> 概念は理解しています。たとえばタイムラインで投稿 100 件を取った後、各投稿の画像を `SELECT * FROM post_images WHERE post_id = ?` で1件ずつ取ると、合計101クエリになる、というのが N+1 です。
>
> **正直に言うと、現状の Eien はここがまだ N+1 です。**`ListPostImages` が単一 post_id を引数に取る実装になっているため、一覧画面でループになっています。
> 直す方法は分かっていて、(a) クエリを `WHERE post_id = ANY($1)` で配列を受けるように変えてハンドラ側で post_id ごとにグループ化、もしくは (b) `posts LEFT JOIN post_images` で JOIN して取得、のどちらかです。次のリファクタで対応予定です。

**面接戦略**：「正直に弱点を言える」は基礎理解と誠実さの両方を示せるので、ここはあえて隠さない方が評価が上がる。

## 5. アーキテクチャ・設計

### Q5-1. バックエンドの構成を教えてください。

> **レイヤードアーキテクチャ**を採用しました。
>
> ```
> handler (HTTP) → service (ビジネスロジック) → repository (DB)
> ```
>
> Eien では `internal/auth`, `internal/group`, `internal/post`, `internal/notification` のように**機能ドメインで分割**し、その中で handler / service / storage を分けています。
> ポイントは、**handler は HTTP のことしか知らない、repository は DB のことしか知らない**こと。間に service を挟むことで「メンバーじゃない人は投稿できない」のようなビジネスルールが一箇所に集まります。

---

### Q5-2. インターフェースを使った設計はありますか？

> 画像ストレージで使っています。`ImageStore` というインターフェースを切って、開発では `LocalImageStore`（ローカルディスク保存）、本番では将来 `R2ImageStore`（Cloudflare R2）に差し替える設計です。
>
> ```go
> type ImageStore interface {
>     Save(ctx context.Context, content io.Reader, contentType string) (publicURL string, err error)
> }
> ```
>
> ハンドラは `ImageStore` インターフェースだけを知っていればよく、本番／開発の切り替えは `main.go` の DI 部分だけで完結します。**依存性逆転**ですね。

---

### Q5-3. フロントエンドの状態管理は？

> サーバ状態は **TanStack Query**、UIだけのローカル状態は **React の useState** で済ませています。
> Redux は導入していません。理由は、Eien のグローバル状態の大半が「サーバから取ってきたデータ」で、TanStack Query がキャッシュ・再フェッチ・楽観的更新まで全部やってくれるからです。
> 認証ユーザー情報も `useAuth()` というフックで `useQuery(["auth", "me"])` を叩く形にしているので、ログアウト時はキャッシュを invalidate するだけで全画面に反映されます。

---

### Q5-4. ルーティングはどうしてる？

> React Router v7 です。`<ProtectedRoute>` というラッパーコンポーネントを作って、その下に「認証必須のルートをすべてネスト」する構成にしました。
> `<ProtectedRoute>` は `useAuth()` の結果を見て、未ログインなら `<Navigate to="/login" />` に飛ばします。これでルートごとに認証チェックを書かなくて済みます。

---

## 6. 苦労した点

### Q6-1. 一番苦労したのはどこですか？

> **誕生日通知の cron ジョブの設計**です。
> 「7時 JST に今日が誕生日のユーザーを取得してメール送る」と書くと一行ですが、考えることが多くて：
> (1) サーバが複数台になったら同じメールが2回送られる
> (2) 送信失敗したらどうするか
> (3) タイムゾーンをどこで吸収するか（DB は UTC、ユーザーは JST）
>
> Eien では、(2)(3) を `email_logs` テーブルで対応しました。送信前に「今日この種類のメールをこのユーザーに送ったか」を確認し、なければ送って `email_logs` に INSERT。これで二重送信が防げますし、失敗時はログを見てリトライできます。
> (1) は今は `min_machines_running = 1` で常時1台運用にしてかわしています。将来複数台になったら**分散ロック**（PostgreSQL のアドバイザリーロック等）で解決する想定です。

---

### Q6-2. 詰まって解決した具体例は？

> セッション Cookie がフロントから送られない問題ですね。
> ローカルで `localhost:5173`（Vite）→ `localhost:8080`（Go）に fetch すると、デフォルトでは Cookie が乗らない。`credentials: "include"` を fetch に付けるのと、サーバ側で `SameSite=Lax` を明示するのと、CORS を `AllowCredentials: true` で設定する、の3点セットを揃える必要があると気づくのに時間がかかりました。

---

### Q6-3. 失敗から学んだことは？

> 最初に**マイグレーションを手で書いていた**ことです。途中で `golang-migrate` を導入して「up/down ファイルでバージョン管理する」形に切り替えました。手書きは一度本番投入したら戻せないので、最初からツールを使うべきでした。

---

## 8. 基礎知識 — 詰まったら詰みやすい質問

### Q8-1. REST API とは？

> リソース指向で、HTTPメソッドの意味で操作を表現する設計スタイルです。
> Eien なら `POST /api/groups/:id/posts`（作成）、`GET /api/groups/:id/posts`（一覧）、`DELETE /api/posts/:id`（削除）のように、URL がリソースを表し、メソッドが動詞を表します。

---

### Q8-2. SQL インジェクションとは？どう防いだ？

> ユーザー入力をそのまま SQL 文字列に連結すると、入力に SQL の構文を混ぜられて意図しないクエリが実行される攻撃です。例：`' OR '1'='1` でログインを突破される。
> 防ぐ方法は **プレースホルダ（パラメータバインド）** を使うこと。SQL の構造を先に決めて、値を別パラメータとして渡せば、値部分は SQL として解釈されません。
> Eien は sqlc 経由で常にプレースホルダ（`$1, $2`）を使っているので、原理的に発生しません。

---

### Q8-3. XSS と CSRF の違いは？

> **XSS（Cross-Site Scripting）** は、攻撃者が悪意あるスクリプトを被害者のブラウザで実行させる攻撃。対策は出力エスケープ。React はデフォルトで全部エスケープしてくれます。
>
> **CSRF（Cross-Site Request Forgery）** は、ログイン中のユーザーのブラウザを利用して、意図しないリクエストを攻撃者のサイトから送信させる攻撃。対策は CSRF トークンの検証や、`SameSite=Lax/Strict` Cookie 属性。Eien は SameSite=Lax で大半をカバーしていますが、完全ではないので将来トークン検証も入れます。

---

### Q8-4. HTTP のステータスコード、よく使うものは？

> 200 OK / 201 Created / 204 No Content / 400 Bad Request / 401 Unauthorized / 403 Forbidden / 404 Not Found / 409 Conflict / 500 Internal Server Error。
>
> Eien では、未ログインなら 401、ログイン済みだが権限がない（他人のグループに投稿しようとした）なら 403、と使い分けています。

---

### Q8-5. トランザクションって何？

> 複数の DB 操作を「全部成功する or 全部なかったことにする」単位でまとめる機能です。ACID 特性のうち**原子性（Atomicity）**を担保します。
> Eien では「投稿作成 + その投稿の画像レコード作成」を1つのトランザクションで実行しています。途中で画像 INSERT が失敗したら、投稿自体もロールバックして整合性を保ちます。

---

### Q8-6. インデックスは何でも貼ればいい？

> いいえ。**読み取りは速くなりますが、書き込みが遅くなり、ストレージも食う**ので、頻繁にクエリされるカラムにだけ貼るのが鉄則です。
> 特に複合インデックスは「カラム順」が重要で、`(group_id, created_at DESC)` は「`WHERE group_id = ? ORDER BY created_at DESC`」には効きますが、「`WHERE created_at = ?`」だけのクエリには効きません。

---

### Q8-7. Docker って何のために使ってる？

> 開発環境を「自分の Mac でも、CI でも、本番でも同じように動かす」ためです。Eien では `docker-compose.yml` で Postgres と Mailhog を一発起動できるようにしています。本番では Go バイナリを Docker イメージにして Fly.io にデプロイ。
> マルチステージビルドで、ビルド用イメージとランタイム用イメージを分けてサイズを小さくしています。

---

### Q8-8. CI/CD は何をやっている？

> GitHub Actions で、PR時に lint + build を走らせ、main マージで Fly.io への自動デプロイをトリガーする想定です。デプロイ前に DB マイグレーションは Go プロセス起動時に自動実行する設計（`db/migrations` を見て自動で適用）。
>
> ※ 「想定」と濁したのは、CI ファイルがまだ完成していない場合に備えて。完全に動いてれば「やっています」と言い切る。

## 9. 学習姿勢・キャリア質問

### Q9-1. 知らない技術が出てきたらどう調べますか？

> 3段階で進めます。
> (1) **公式ドキュメントを読む**（一次情報、英語でも読む）
> (2) **小さく動かす**（写経 or 公式チュートリアル）
> (3) **自分のプロジェクトに組み込む**（理解の本質はここで初めて分かる）
>
> Eien では sqlc を入れたとき、まず公式の Getting Started を 1日でこなしてから既存の Eien に組み込みました。

---

### Q9-2. 一人で詰まったらどうしますか？

> まず**エラーメッセージを正確に読む**。
> 次に**最小再現コード**を作る。問題を小さく分離できれば解けることが多いです。
> それでもダメなら、(a) 公式 Issue、(b) Stack Overflow、(c) AI ツール（Claude や ChatGPT に最小再現コードを貼って聞く）を順に使います。最終的にはチームメンバーに聞きますが、まず自分で分離する努力をしてからにします。

---

### Q9-3. インターンで何を学びたいですか？

> 個人開発では分からない「**チーム開発の作法**」を学びたいです。具体的には、(1) コードレビューでどんな観点を見るか、(2) 大きい既存コードベースに変更を入れる時の進め方、(3) 障害対応・運用の現場感、です。
> 自分は要件定義から自分で書いてきたので、逆に「他人の決めた要件・既存の設計」に合わせて手を動かす経験が今いちばん欲しいと思っています。
