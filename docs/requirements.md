## 2. ユーザーストーリー

### 2.1 アカウント・認証

| ID | ストーリー |
| --- | --- |
| US-001 | **ユーザーとして**、メールアドレスとパスワードで新規登録したい。**なぜなら**、自分のアカウントを作る必要があるから。 |
| US-002 | **登録済みユーザーとして**、ログイン/ログアウトしたい。**なぜなら**、いつでも自分のアカウントにアクセス・離脱できるようにしたいから。 |
| US-003 | **ユーザーとして**、ログイン状態を一定期間保持してほしい。**なぜなら**、たまにしか開かないアプリでも毎回パスワードを入れずに済ませたいから。 |

### 2.2 グループ管理

| ID | ストーリー |
| --- | --- |
| US-004 | **ユーザーとして**、新しいグループを作成したい。**なぜなら**、自分の所属コミュニティ（部活、家族、サークル等）ごとに場を分けたいから。 |
| US-005 | **ユーザーとして**、招待リンクから既存グループに参加したい。**なぜなら**、知り合いから招待された場に参加するため。 |
| US-006 | **グループメンバーとして**、招待リンクを発行して仲間を呼びたい。**なぜなら**、信頼できる人だけ参加できるクローズド設計を維持しつつメンバーを増やすため。 |
| US-007 | **ユーザーとして**、複数のグループに同時に所属したい。**なぜなら**、人生のコミュニティは1つではないから。 |
| US-008 | **ユーザーとして**、自分が所属するグループ一覧を見たい。**なぜなら**、どこに自分がいるかを把握したいから。 |

### 2.3 グループ別プロフィール

| ID | ストーリー |
| --- | --- |
| US-009 | **ユーザーとして**、グループごとに表示名とアイコンを切り替えたい。**なぜなら**、部活では「たかしさん」、家族では「お兄ちゃん」のように呼び名を変えたいから。 |
| US-010 | **ユーザーとして**、他メンバーのプロフィール（そのグループでの表示）を閲覧したい。**なぜなら**、誰の投稿か把握したいから。 |

### 2.4 誕生日トリガー通知（独自機能）

| ID | ストーリー |
| --- | --- |
| US-011 | **ユーザーとして**、自分の誕生日にメール通知を受け取りたい。**なぜなら**、Eienを開くきっかけにしたいから。 |
| US-012 | **ユーザーとして**、グループ仲間の誕生日にメール通知を受け取りたい。**なぜなら**、お祝いを伝える機会を逃したくないから。 |
| US-013 | **ユーザーとして**、誕生日の人がいる日はアプリ内で豪華に表示してほしい。**なぜなら**、特別な日であることを視覚的に感じたいから。 |

### 2.5 通知設定

| ID | ストーリー |
| --- | --- |
| US-014 | **ユーザーとして**、誕生日通知の対象を選びたい（自分のみ / 自分＋仲間 / 通知なし）。**なぜなら**、メールの量を自分で制御したいから。 |
| US-015 | **ユーザーとして**、新規投稿があるたびに通知を受け取るかどうかを選びたい。**なぜなら**、投稿頻度の低いSNSとはいえ、人によっては都度知りたいから。 |

### 2.6 イベント投稿

| ID | ストーリー |
| --- | --- |
| US-016 | **ユーザーとして**、写真と文章を組み合わせて投稿したい。**なぜなら**、人生の節目を視覚的・テキスト的に記録したいから。 |
| US-017 | **ユーザーとして**、投稿時にどのグループに公開するか選択したい。**なぜなら**、内容によって共有相手を分けたいから。 |
| US-018 | **ユーザーとして**、自分の投稿を削除したい。**なぜなら**、公開を取り下げたい場面があるから。 |

### 2.7 タイムライン・一覧表示

| ID | ストーリー |
| --- | --- |
| US-019 | **ユーザーとして**、所属グループの投稿を時系列で見たい。**なぜなら**、最新の出来事を把握したいから。 |
| US-020 | **ユーザーとして**、投稿を一覧（カード/グリッド型）で俯瞰したい。**なぜなら**、過去のイベントをアルバム的に振り返りたいから。 |
| US-021 | **ユーザーとして**、過去の投稿を遡って読みたい。**なぜなら**、見逃した投稿を確認したいから。 |

### 2.8 インタラクション

| ID | ストーリー |
| --- | --- |
| US-022 | **ユーザーとして**、投稿に返信したい。**なぜなら**、お祝いやコメントを伝えたいから。 |
| US-023 | **ユーザーとして**、投稿にリアクション（絵文字等）を付けたい。**なぜなら**、軽い反応で気持ちを伝えたいから。 |

### 2.9 グループチャット

| ID | ストーリー |
| --- | --- |
| US-024 | **ユーザーとして**、所属グループの全員チャットでメッセージを送りたい。**なぜなら**、投稿ほどのイベントではない雑談や調整をしたいから。 |
| US-025 | **ユーザーとして**、チャットの過去ログを遡って読みたい。**なぜなら**、参加していなかった会話を後から把握したいから。 |

### 2.10 イベント招待一括メール

| ID | ストーリー |
| --- | --- |
| US-026 | **ユーザーとして**、グループメンバーから招待先を選び、本文＋URLを記載したメールを一括送信したい。**なぜなら**、結婚式や同窓会の案内を効率よく届けたいから。 |

## 3. MoSCoW 優先度マトリクス

> **方針**：期間は厳密に切らず、進捗ベースで進める。
> Phase 0（MVP）でEienらしさを最低限表現し、Phase 1で拡張する。

### Must（Phase 0 / MVPに必須）

**Eienのコアコンセプトを最小構成で体現する**ことを目的とする。

- US-001, US-002, US-003 : 認証
- US-004, US-005, US-007, US-008 : グループ作成・参加・一覧
- US-009 : グループ別プロフィール（表示名のみ。アイコンはShouldでも可）
- US-016, US-017, US-018 : 投稿（テキスト＋画像、グループ選択、削除）
- US-019, US-021 : 時系列タイムライン・遡り
- US-011 : 自分の誕生日メール通知（Eienのコンセプト体現）
- US-013 : 誕生日豪華表示

### Should（Phase 1 / MVP後すぐに追加）

- US-006 : 招待リンク発行（※Mustに上げる選択肢あり）
- US-010 : 他人のプロフィール閲覧
- US-012 : 仲間の誕生日メール通知
- US-014, US-015 : 通知設定
- US-020 : 一覧表示
- US-022 : 返信
- US-023 : リアクション
- **US-024, US-025 : グループチャット**（明確にPhase 1扱い／2026-05-03 決定）

### Could（時間と相談）

- US-026 : イベント招待一括メール

### Won't（今回はやらない）

- 動画投稿、ライブ配信
- DM（1対1メッセージ）
- イベント招待のRSVP（出欠機能） ※将来アプリ内に組み込む候補
- 検索機能
- 課金、広告、レコメンドAI
- ハッシュタグ、フォロー機能（既存SNS的な要素）
- アカウント削除、退会フロー（将来必須だがMVPでは未実装）

## 5. 非機能要件

> 「機能が何をするか」ではなく「どんな品質で動くか」を定義する節。
> 設計フェーズより前に方針を決めることで、後の手戻りを防ぐ。

### 5.1 対応デバイス・ブラウザ

- **想定**：スマホメイン ＋ PCサブ（**レスポンシブWebアプリ**として実装）
- **モバイルアプリ（ネイティブ）は作らない**：Web完結
- **サポートブラウザ**：
  - PC：Chrome / Safari / Firefox / Edge の最新2バージョン
  - モバイル：iOS Safari、Android Chrome の最新2バージョン
- **画面幅基準**：
  - 〜768px：モバイルレイアウト
  - 769px〜：デスクトップレイアウト

### 5.2 セキュリティ

OWASPベースの**標準レベル**を満たす。

- **通信**：HTTPS必須（HTTPは403リダイレクト）
- **パスワード保管**：bcrypt等のハッシュ関数で保存（平文・可逆暗号は不可）
- **セッション**：HttpOnly + Secure属性付きCookie、適切な有効期限
- **CSRF対策**：状態変更操作にトークン検証
- **XSS対策**：出力時のエスケープを徹底、CSP設定
- **SQLインジェクション対策**：プレースホルダ/ORMを必ず使用
- **認可制御**：ユーザーは自分が所属するグループのデータのみアクセス可
- **招待リンクトークン**：推測困難なランダム文字列（最低128bit相当）
- **ファイルアップロード**：拡張子・MIMEタイプ・サイズ検証
- **対象外（Phase 1以降検討）**：MFA、画像の暗号化保管、レート制限、監査ログ

### 5.3 パフォーマンス

低頻度利用前提のため、過度な最適化は不要。**現実的な体感品質**を目標。

| 指標 | 目標値 |
| --- | --- |
| トップページ初期表示 | 3秒以内（モバイル4G想定） |
| タイムライン読み込み | 2秒以内 |
| 投稿送信完了 | 2秒以内 |
| 画像アップロード | 5秒以内（〜3MB想定） |
| タイムラインのページング | 20件ずつ、追加読み込み |

### 5.4 可用性

個人プロジェクトとして現実的なレベルに設定。

- **稼働率目標**：99%程度（月あたり最大7時間ほどのダウン許容）
- **計画停止**：許容（事前通知できれば）
- **障害時**：重大障害は数時間以内の復旧を目指す
- **SLA等の対外保証はなし**

### 5.5 データ保持

「永遠の仲間」のコンセプト上、**思い出の集積に価値**を置く。

- **投稿・チャット**：長期保存（実質永久）。自動削除は行わない。
- **画像**：投稿に紐付く形で永続保存
- **退会・アカウント削除時の扱い**：Phase 1以降で詳細設計（GDPR的な"忘れられる権利"含む）
- **バックアップ**：日次で取得（インフラ設計で詳細決定）

### 5.6 メール送信（誕生日通知の根幹）

- **誕生日通知の送信時刻**：当日朝7:00 JST（変更余地あり）
- **送信失敗時**：最大3回リトライ
- **送信元アドレス**：固定（noreply@<ドメイン> 等）
- **受信側のスパム判定対策**：SPF / DKIM 設定（設計フェーズで詳細）

### 5.7 アクセシビリティ

最低限のアクセシビリティを確保。WCAG 2.1 Level A相当を目指す。

- キーボードのみで主要操作が可能
- 画像にalt属性を必ず設定
- 文字色と背景色のコントラスト比を確保

### 5.8 ログ・監視

最低限の運用に耐えるレベル。

- アプリケーションエラーログ（Sentry等の利用検討）
- 認証失敗ログ
- メール送信成功/失敗ログ
- アクセスログはホスティング基本機能に任せる

### 5.9 国際化・タイムゾーン

- **言語**：日本語のみ
- **タイムゾーン**：JST（UTC+9）固定
- **日付フォーマット**：和暦不要、`YYYY年MM月DD日` 形式

### 5.10 想定スケール

- **1グループあたりのメンバー数**：10〜50名想定（最大100名程度まで）
- **グループ数**：数十〜数百
- **同時接続数**：数十程度（低頻度利用のため）
- **総ユーザー数**：当面1,000名以下を想定

## 6. 技術スタック

> 「なぜこの技術を選ぶのか」を説明できる状態をゴールとする（ポートフォリオ要件）。

### 6.1 全体構成サマリー

| レイヤー | 採用技術 |
| --- | --- |
| フロント言語 | TypeScript |
| フロントビルド | Vite |
| フロントUI | React 19 |
| ルーティング | React Router v7 |
| サーバ状態 | TanStack Query (React Query) |
| スタイリング | Tailwind CSS |
| フォーム | React Hook Form |
| バック言語 | Go |
| バックフレームワーク | Echo |
| DB | PostgreSQL |
| DBクエリ層 | sqlc |
| マイグレーション | golang-migrate |
| 認証 | 自前実装（セッションCookie方式） |
| 画像ストレージ | 開発:ローカル / 本番:Cloudflare R2 (S3互換) |
| メール送信 | 開発:Mailhog / 本番:Resend |
| コンテナ | Docker + docker-compose |
| デプロイ先 | Fly.io（アプリ＋PostgreSQL同居） |
| CI/CD | GitHub Actions |
| エラー監視 | Sentry（無料枠） |
| API仕様管理 | OpenAPI 3.0 → TypeScript型自動生成 |

### 6.2 フロントエンド

- **TypeScript**：型安全。ポートフォリオでは事実上必須。
- **Vite**：CRAは時代遅れ。Viteは起動・HMRが圧倒的に速い。
- **React 19**：採用確定（実装時の最新版に合わせて当初の v18 から更新）。
- **React Router v7**：SPAルーティングのデファクト（実装時の最新版に合わせて当初の v6 から更新）。
- **TanStack Query**：API呼び出しのキャッシュ・再取得・楽観的UIをこれに任せる。useEffect+fetchの自前実装は地獄なので最初から導入。
- **Tailwind CSS**：ユーティリティファースト。CSS命名で悩む時間がほぼゼロになる。Eienのようなレスポンシブ要件と相性◎。
- **React Hook Form**：軽量・パフォーマンス◎。バリデーションも書きやすい。

### 6.3 バックエンド

- **Go**：採用確定。並行処理（誕生日メール一括送信）を言語機能で書けるのが強み。Dockerイメージが軽量。
- **Echo**：必要十分な機能（ルーティング、ミドルウェア、バインディング）を提供。Gin との詳細比較は行わず、本プロジェクトの規模ではどちらでも要件は満たせる前提で Echo を選んだ。

### 6.4 データベース・データアクセス

- **PostgreSQL**：SNSに必要なリレーション・JSONB・全文検索などを一通り持つ。Eienのマルチグループ設計と相性◎。
- **sqlc**：SQLを書くと型安全なGoコードが自動生成される。SQLの学習価値を保ちつつ、ORMの便利さも得られる。
- **golang-migrate**：マイグレーションのデファクト。バージョン管理されたDBスキーマ変更が可能。

### 6.5 認証・認可

- **自前実装（セッションCookie方式）**：学習目的のため自前実装。
  - JWTではなくセッションCookieを推奨：取り消しが効く、CSRF対策がHTTPフレームワークの標準機能で済む。
  - パスワードハッシュは `bcrypt`。
  - セッション保存はPostgreSQL（Redisは規模を考えると過剰）。
- **認可**：「ユーザーは自分が所属するグループのデータのみアクセス可」をミドルウェア層で強制。

### 6.6 画像・メディア

- **開発**：Goアプリのローカルファイルシステムに保存（`./uploads/`）。
- **本番**：Cloudflare R2（S3互換、エグレス料金無料、コスト最小）。
- **画像処理**：Goの `image` パッケージでリサイズ。投稿時にサーバ側で複数サイズ生成（サムネイル＋オリジナル）。

### 6.7 メール送信

- **開発**：Mailhog（Dockerでローカル起動するSMTPサーバ＋Web UI）。実際にメールを送らずに送信内容を確認できる。
- **本番**：Resend（無料枠：月3,000通）。開発者体験が良くSPF/DKIM設定も簡単。
- **誕生日通知のスケジュール実行**：cron形式のジョブをGoのバックグラウンドゴルーチンか、Fly.ioの `[deploy] release_command` で実装。

### 6.8 インフラ・デプロイ

- **Docker + docker-compose**：ローカル開発でフロント・バック・PostgreSQL・Mailhogを一括起動。
- **Fly.io**：本番ホスティング。
  - 理由：Dockerコンテナをそのままデプロイ可、無料枠で開始可、Postgres も同プラットフォームで立てられる、Goとの相性が良い。
  - Tokyo (NRT) リージョンが選べる。
- **構成**：Fly.io上に「Go バックエンドコンテナ」「フロントエンド静的ファイル配信」「Postgres」を配置。フロントはバック側で配信してもよいし、Cloudflare PagesやNetlifyで分離してもよい。

### 6.9 CI/CD・コード品質

- **GitHub Actions**：CI/CDのデファクト。パブリックリポジトリは無料。
  - PR時：lint・テスト・ビルド
  - mainマージ時：Fly.ioへ自動デプロイ
- **Goのlint**：`golangci-lint`
- **TypeScriptのlint・format**：ESLint + Prettier
- **pre-commit フック**：`gitleaks` で機密情報のうっかりコミット防止

### 6.10 監視・ロギング

- **Sentry**：エラー監視。無料枠（月5,000イベント）で十分。
- **アプリケーションログ**：Goは構造化ログの `slog`（標準ライブラリ）を使用。
- **メール送信ログ**：成功/失敗をDBに記録。

### 6.11 API仕様管理

- **OpenAPI 3.0** でAPIスキーマを定義。
- フロント側で `openapi-typescript` を使ってTypeScript型を自動生成。
- これによりGo（バック）とTS（フロント）の型の二重管理を解消。

## 7. スコープ外（明示）

セクション3「Won't」の内容を、参照しやすい形で再掲。

### 7.1 機能スコープ外

| 項目 | 理由 |
| --- | --- |
| 動画投稿、ライブ配信 | スコープ過大、ストレージコストも増 |
| DM（1対1メッセージ） | 投稿×グループチャットで代替可 |
| 検索機能 | データ量増えてから必要に応じて |
| イベント招待のRSVP（出欠機能） | Phase 2以降の検討候補 |
| 課金、広告、レコメンドAI | 本プロジェクトの目的に合わない |
| ハッシュタグ、フォロー機能 | クローズドSNSにはそぐわない |
| 多言語対応 | 日本のみ想定 |
| ネイティブモバイルアプリ | レスポンシブWebで代替 |

### 7.2 非機能スコープ外（MVP段階）

| 項目 | 理由 |
| --- | --- |
| 多要素認証（MFA） | 標準セキュリティで十分、Phase 1検討 |
| 画像の暗号化保管 | 標準セキュリティで十分 |
| アカウント削除フロー（GDPR的"忘れられる権利"） | Phase 1で詳細設計 |
| 詳細な監査ログ | 個人プロジェクトには過剰 |
| 99.9%以上の可用性 | 個人プロジェクトには過剰 |
| マルチリージョン展開 | 日本のみ想定 |
